# LinkSnip MVP 요구사항

## 1. 목표와 범위

LinkSnip은 유효한 HTTP(S) URL을 짧은 코드로 저장하고, 짧은 URL로 접근한 사용자를 원본 URL로 리다이렉트하는 서비스다.

MVP에서 제공하는 기능은 다음과 같다.

- 단축 링크 생성
- 단축 링크 정보 조회
- 단축 링크를 통한 리다이렉트
- 단축 링크 삭제
- 선택적 만료 시각 설정

사용자 계정, 사용자 지정 단축 코드, 통계, QR 코드, 미리보기 페이지, 일괄 생성은 MVP 범위에서 제외한다.

## 2. 용어와 데이터

단축 링크는 다음 정보를 가진다.

| 필드 | 설명 | 제약 |
| --- | --- | --- |
| `code` | 시스템이 생성한 식별자 | Base62 문자 7개, 전체 링크 중 유일 |
| `url` | 원본 URL | 절대 `http` 또는 `https` URL, 최대 2048자 |
| `shortUrl` | 외부에 제공할 단축 URL | `{PUBLIC_BASE_URL}/{code}` |
| `createdAt` | 생성 시각 | UTC ISO 8601 문자열 |
| `expiresAt` | 만료 시각 | 생략 가능, 지정 시 생성 시각보다 미래 |

서버는 동일한 원본 URL 요청에도 새 단축 링크를 생성한다. URL 정규화나 중복 제거는 하지 않는다.

## 3. 기능 요구사항과 수용 기준

### R1. 단축 링크 생성

- 클라이언트는 원본 URL과 선택적인 만료 시각을 제출할 수 있다.
- 유효한 요청이면 서버는 새 코드를 생성하고 `201 Created`를 반환한다.
- `Location` 헤더는 생성된 링크의 정보 조회 경로인 `/api/v1/links/{code}`를 가리킨다.
- 요청 본문이 없거나, 알 수 없는 필드가 있거나, URL 또는 만료 시각이 제약을 위반하면 `400 Bad Request`를 반환한다.

### R2. 단축 링크 정보 조회

- 존재하며 만료되지 않은 코드이면 저장된 링크 정보를 `200 OK`로 반환한다.
- 존재하지 않거나 삭제된 코드이면 `404 Not Found`를 반환한다.
- 만료된 코드이면 `410 Gone`을 반환한다.

### R3. 리다이렉트

- 존재하며 만료되지 않은 코드이면 원본 URL을 `Location` 헤더에 담아 `302 Found`를 반환한다.
- 존재하지 않거나 삭제된 코드이면 `404 Not Found`를 반환한다.
- 만료된 코드이면 `410 Gone`을 반환한다.
- 원본 URL의 쿼리 문자열과 프래그먼트는 저장된 그대로 유지한다.

### R4. 단축 링크 삭제

- 존재하는 코드이면 링크를 삭제하고 본문 없이 `204 No Content`를 반환한다.
- 존재하지 않거나 이미 삭제된 코드이면 `404 Not Found`를 반환한다.
- 삭제 성공 후 해당 코드의 조회와 리다이렉트는 모두 `404 Not Found`를 반환한다.

### R5. 공통 오류 응답

- API 오류는 `application/problem+json` 형식을 사용한다.
- 오류 응답에는 `type`, `title`, `status`, `detail`, `instance`가 포함된다.
- 유효성 검사 오류에는 각 입력 오류를 나타내는 `errors` 배열이 추가된다.
- 서버 내부 정보와 스택 트레이스는 응답에 노출하지 않는다.

## 4. 비기능 요구사항

- 모든 JSON 요청과 응답은 UTF-8을 사용한다.
- 날짜와 시각은 UTC ISO 8601 형식(예: `2026-08-16T12:34:56Z`)을 사용한다.
- 생성된 코드는 대소문자를 구분한다.
- 코드 생성 충돌이 발생하면 서버가 재시도하며, 클라이언트에는 충돌을 노출하지 않는다.
- 저장소 오류 등 예상하지 못한 실패는 공통 오류 형식의 `500 Internal Server Error`로 반환한다.
- `PUBLIC_BASE_URL`은 배포 환경에서 설정하며 응답의 `shortUrl` 생성에 사용한다.

## 5. API 계약의 기준

기계 판독 가능한 계약의 기준(source of truth)은 [`openapi.yaml`](./openapi.yaml)이다. 구현은 이 문서의 수용 기준과 OpenAPI 계약을 모두 만족해야 하며, 서로 충돌할 경우 구현 전에 계약을 먼저 수정한다.

## 6. 검증 계획

구현 후 아래 항목을 서로 독립적인 테스트로 검증한다.

1. OpenAPI 문서를 파서와 린터로 검사해 문법, 참조, 스키마 오류가 없는지 확인한다.
2. 정상 생성 요청이 `201`, `Location` 헤더, 7자리 Base62 코드와 올바른 `shortUrl`을 반환하는지 계약 테스트한다.
3. 잘못된 스킴, 상대 URL, 2048자 초과 URL, 과거 만료 시각, 알 수 없는 필드가 각각 `400` 문제 상세 응답을 반환하는지 테스트한다.
4. 생성한 코드를 조회했을 때 `200`과 생성 당시 데이터가 반환되는지 테스트한다.
5. 생성한 코드로 접근했을 때 `302`와 원본 URL 그대로의 `Location` 헤더가 반환되는지 테스트한다.
6. 삭제가 `204`를 반환하고, 이후 조회와 리다이렉트가 각각 `404`를 반환하는지 테스트한다.
7. 만료 시각 전에는 조회와 리다이렉트가 성공하고, 시각을 만료 이후로 이동시키면 둘 다 `410`을 반환하는지 가짜 시계로 테스트한다.
8. 코드 생성기를 충돌하도록 대체했을 때 재시도 후 유일한 코드가 저장되는지 단위 테스트한다.
