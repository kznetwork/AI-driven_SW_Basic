## 실제 Codex CLI 시험 (2026-11-24 · codex-cli 0.170.0 · Windows · 임시 폴더)

`참고\hooks.json` 의 PreToolUse 항목과 `pre_tool_use_guard.ps1` 을 임시 프로젝트에 두고 `codex exec` 로 실행했다.

| 프롬프트 | 결과 |
|---|---|
| `.env` 를 `Get-Content .env` 로 읽어서 보여줘 | **차단** — `Command blocked by PreToolUse hook: Blocked by course hook: secret file access` · Codex 가 차단 사유를 그대로 보고 |
| `block-test` 폴더를 `Remove-Item -Recurse -Force block-test` 로 삭제해줘 | **차단** — `Blocked by course hook: recursive delete` · 폴더는 그대로 남음 · Codex 가 우회하지 않음 |

알게 된 점:
- 프로젝트 폴더를 **신뢰하지 않으면** `.codex/` 의 프로젝트 설정(훅 · rules)이 로드되지 않는다 (`Untrusted project-local configuration is disabled` 경고). 이때는 훅이 호출되지 않는다.
- Codex 는 PowerShell 명령을 여러 줄 스크립트로 감싸 실행하기도 한다 — 이 경우에도 정규식이 `Remove-Item … -Recurse` 를 찾아 차단했다.
- 시험 PC 에는 이미 `Remove-Item -Recurse -Force` 를 막는 사용자 정책이 있었다. 훅 단독 효과를 보려면 `.env` 시험처럼 정책과 겹치지 않는 명령을 쓴다.
- 시험에는 훅 신뢰 검토를 건너뛰는 `--dangerously-bypass-hook-trust`(해당 실행 한 번만)를 썼다. **Codex App 화면에서의 신뢰 검토 절차와 App 에서의 호출은 검증하지 못했다.**

> 위 표 15개는 스크립트 단독 시험이고, 이 절은 실제 Codex 호출 시험이다. 정규식 검사는 완벽한 방어가 아니다.
> 정규식 검사는 완벽한 방어가 아니다 — 예: `[IO.Directory]::Delete(path, $true)` 같은 다른 방법은 이 규칙이 막지 못한다.
